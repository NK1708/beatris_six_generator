# Bearridge AI Generator — Agent Instructions

## Purpose

Bearridge AI Generator is a local single-user production tool for generating
visually consistent images for a visual novel.

This is NOT a generic AI image generator.

The primary engineering problem is maintaining visual continuity across
50–100+ generated story frames:

- character identity;
- face;
- apparent age;
- body proportions;
- hair;
- outfits;
- locations and architecture;
- props;
- visual style;
- lighting;
- story state;
- continuity between sequential frames.

Gemini is used as an image renderer. Gemini is NOT the memory or source of truth
for the project.

---

## Core Architecture

The fundamental pipeline is:

LOCAL PROJECT STATE
    ↓
REFERENCE RESOLVER
    ↓
PROMPT BUILDER
    ↓
IMAGE PROVIDER
    ↓
GENERATION
    ↓
HUMAN REVIEW
    ↓
LOCKED ASSET
    ↓
LOCAL PROJECT STATE

Do not bypass this pipeline.

Do not replace local project state with persistent Gemini chat history.

Every generation request must be reconstructable from local project data.

---

## Source of Truth

Authoritative project state lives locally in:

- project.sqlite;
- project.json;
- Story State;
- canonical LOCKED references;
- generated asset provenance;
- local project files.

The AI provider must never become the authoritative source of project state.

---

## Project Storage

Every VN project must remain self-contained.

Expected structure:

projects/<project-slug>/
  project.sqlite
  project.json
  bible/
  characters/
  locations/
  props/
  style/
  story/
  states/
  frames/
  generations/
  references/

A project folder must be portable as one unit.

app.sqlite may contain only application-level project registry information.

Never move production project entities back into a global database.

---

## AI Provider Rule

The application must remain provider-independent.

Domain logic must not depend directly on Gemini SDK implementation details.

Use the ImageProvider abstraction.

Gemini is currently the primary provider, but future providers must be possible
without redesigning the domain layer.

---

## Reference Rule

Canonical references are versioned.

Lifecycle:

DRAFT
→ APPROVED
→ LOCKED
→ DEPRECATED

REJECTED is also possible.

Uploading or generating a reference NEVER automatically makes it canonical.

Only LOCKED references may be selected automatically by ReferenceResolver for
production generation.

When a new version becomes LOCKED:

old LOCKED → DEPRECATED
new version → LOCKED

Historical Generation provenance must continue pointing to the exact reference
versions actually used.

Never rewrite historical provenance when canonical references change.

---

## Canonical Priority

Canonical references are authoritative.

Priority conceptually is:

1. canonical character identity;
2. canonical outfit;
3. canonical location / location angle;
4. canonical important props;
5. canonical style;
6. previous LOCKED frame.

Previous frame is continuity evidence, not canonical truth.

If a previous generated frame conflicts with canonical identity, outfit,
location or style references, canonical references win.

---

## Frame / Panel / Screen

These concepts MUST remain separate.

### Frame

A Frame is an individual story image generated by AI.

Gemini generates Frames.

### Panel

A Panel is a region of an eventual visual novel Screen that displays a Frame.

Panels may have arbitrary dimensions and aspect ratios.

### Screen

A Screen is the final composed visual novel page/screen containing one or more
Panels.

The application does NOT currently generate complete Screens with Gemini.

Do not merge Frame, Panel and Screen into one entity.

---

## Geometry Rule

Target Panel geometry and AI generation geometry are different concepts.

Example:

target panel:
1200 × 500

does NOT imply:

Gemini must generate exactly 1200 × 500.

Correct pipeline:

TARGET PANEL GEOMETRY
    ↓
GENERATION GEOMETRY RESOLVER
    ↓
SUPPORTED GEMINI ASPECT RATIO / RESOLUTION
    ↓
GENERATION
    ↓
FUTURE CROP / RESIZE
    ↓
FINAL PANEL ASSET

Frames may have different target aspect ratios.

Do not impose one global 16:9 format on the project.

Project default geometry is only a fallback.

---

## Story State

Story State is authoritative structured continuity data.

Examples:

- time;
- character presence;
- current outfit;
- hair state;
- held props;
- environment state;
- lights;
- doors;
- windows;
- curtains;
- important story facts.

Do not rely on Gemini remembering these facts from previous requests.

Story State must be injected into generation context when relevant.

---

## Prompt Builder

Frames should store concise creative intent such as:

- action;
- camera;
- composition;
- expression;
- lighting;
- continuity notes.

Do NOT require users to manually maintain giant prompts.

PromptBuilder must reconstruct the production prompt from:

- Frame;
- Story State;
- Characters;
- Outfits;
- Location;
- Props;
- Style;
- resolved references;
- geometry.

---

## Reference Resolver

ReferenceResolver should provide the minimum relevant canonical context required
for a frame.

Do not blindly send every project image to the provider.

The current resolver may be simple, but its architecture must allow future
selection based on:

- camera angle;
- character orientation;
- full body vs close-up;
- outfit orientation;
- location angle;
- props;
- scene requirements.

Do not implement semantic selection unless explicitly requested.

---

## Provenance

Every generation must remain reproducible and auditable.

Store at minimum:

- provider;
- model;
- generation mode;
- prompt;
- exact reference versions;
- reference roles;
- Story State snapshot;
- Frame snapshot;
- target geometry;
- provider request geometry;
- timestamp;
- generation relationship/parent where applicable.

Never overwrite previous generation results.

---

## Human Review

AI output does not become canonical automatically.

Expected workflow:

GENERATE
→ REVIEW
→ HUMAN QC
→ LOCK

A generated Frame can be used automatically as previous-frame continuity only
after it is LOCKED.

---

## Engineering Rules

Before making architectural changes:

1. inspect the current implementation;
2. inspect README.md;
3. inspect docs/ARCHITECTURE.md;
4. inspect docs/DECISIONS.md;
5. understand existing tests.

Prefer incremental changes over rewrites.

Do not rewrite working architecture unless a concrete problem requires it.

After significant changes run:

npm run typecheck
npm test
npm run build

Fix failures before considering the task complete.

Use strict TypeScript.

Avoid `any` unless required at an external boundary.

Keep domain logic out of React components.

Keep provider-specific code out of domain services.

Validate external input.

Do not expose API keys to the frontend.

Do not log API keys or raw image base64.

## Current Development Goal

The immediate goal is NOT to build every future feature.

The immediate goal is to prove that the pipeline can maintain acceptable visual
consistency across a sequence of approximately 20 generated Frames using real
Gemini image generation.

Engineering work should prioritize making that benchmark reliable,
inspectable and measurable.
